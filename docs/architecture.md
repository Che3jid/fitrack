# 架构与阶段边界

## 当前阶段

第一阶段只提供可运行的工程、计算模块和测试。`main.ts` 是暂时的静态开发预览，不承担业务或模拟已经存在的功能。

## 依赖方向

```text
页面 / 公共组件 → 业务服务 → 存储接口 → 本地适配器 / 未来云适配器
                        → domain 纯计算与模型
```

`domain` 不导入 DOM、localStorage 或网络 API。第二阶段增加 `pages/`、`components/`、`services/`、`storage/`，由实际业务驱动抽象，不引入状态管理框架。

存储接口统一异步；首版本地方案和版本迁移将在第二阶段实现。记录通过稳定 ID 标识，包含 userId、schemaVersion、createdAt、updatedAt。当前没有云账号，未来本地用户标识也不作为服务端授权凭据。

## 规划路由

| Hash 路由 | 用途 |
| --- | --- |
| #/onboarding | 首次设置 |
| #/today | 今日概览 |
| #/diet | 四餐记录 |
| #/training | 训练记录 |
| #/trends | 体重、摄入和热量差趋势 |
| #/profile | 个人资料 |

使用 hash 路由，静态托管无需服务端路由回退。首次使用守卫在第二阶段实现。表单采用独立页面模块或对话框，之后按交互需求确定，不在第一阶段添加空页面。

## 数据约束

- 日期键为 Asia/Shanghai 下的 YYYY-MM-DD，时间戳为 ISO 8601。
- WeightEntry、DailyPlan、DayStatus 按 userId + date 唯一。
- FoodEntry 保存本次食用总量；TrainingEntry 暂只支持手动估算。
- DailyPlan 保存计算结果、输入快照及算法版本，不根据最新个人资料重算过去。
- 当天资料变更更新当天目标；补录过去的体重不能误写当前资料体重，需按日期决定当前体重。
- 每日汇总从原始记录派生，不额外存储重复统计。
- DayStatus 区分尚未记录、记录中、已完成；有记录不自动等于已完成。
- 数据导入必须校验 schemaVersion、单位、日期、范围和 ID，迁移设计需可重试且不重复插入。

## 验收顺序

1. 工程能运行，测试与生产构建通过。
2. 资料保存重启不丢失，当前目标与历史目标隔离。
3. 饮食、训练、体重增删改后汇总正确刷新。
4. 日历窗口、缺失值、备份恢复和手机布局正确。
5. 创建远程开源仓库、CI、部署，再验证 HTTPS 下的 PWA。
